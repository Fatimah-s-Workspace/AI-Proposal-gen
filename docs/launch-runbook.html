Do these in order

The order matters in two places: migrations must land before anything touches production, and DNS changes need hours to propagate so they should be started early. Everything else is independent.

Three migrations have not reached production. The invoice one creates a database sequence, so the app will error on the first payment without it.

npx prisma migrate deploy

Run it against the production DATABASE_URL. Never migrate dev, which is interactive and can reset data.

Prove it

npx prisma migrate status

Must say every migration has been applied. Expect add_document_analysis_notice and add_invoices in the list.

Start first30 min + wait

Do this early: DNS takes hours to propagate, so starting it now means it is ready when you reach the smoke test. Without SPF, DKIM and DMARC, verification emails land in spam — and since new accounts cannot sign in until they confirm, that is signup broken for anyone who does not check their junk folder.

In Brevo: Senders, Domains & Dedicated IPs → Domains → Authenticate. It gives you a DKIM record and a Brevo SPF include. Add both at your DNS host, then add a DMARC record:

Type:  TXT
Host:  _dmarc
Value: v=DMARC1; p=none; rua=mailto:dmarc@yourdomain.com

p=none monitors without rejecting anything. Move to p=quarantine only after a few weeks of clean reports.

Prove it

dig +short TXT yourdomain.com | grep spf
dig +short TXT _dmarc.yourdomain.com
dig +short TXT mail._domainkey.yourdomain.com

All three must return a record. Then send yourself a real signup and check the header shows dkim=pass and spf=pass. Or email mail-tester.com from the app and aim for 9/10 or better.

Blocks launch60 min

Not "check backups are enabled". An untested backup is not a backup — the failure mode is discovering at the worst possible moment that it has been silently backing up nothing useful.

  1. Supabase → Database → Backups. Confirm daily backups exist and note the retention window.
  2. Create a throwaway Supabase project.
  3. Restore yesterday's backup into it.
  4. Query it and compare against production.

Prove it

psql "$RESTORED_URL" -c 'SELECT
  (SELECT count(*) FROM "User")            AS users,
  (SELECT count(*) FROM "Project")         AS projects,
  (SELECT count(*) FROM "TenderDocument")  AS documents,
  (SELECT count(*) FROM "Payment")         AS payments;'

Counts should be close to production, allowing for a day of activity. Zero anywhere means the backup is not capturing what you think. Delete the throwaway project afterwards.

Uploaded files live in Supabase Storage, not the database, and are backed up separately. Check that too — a database restore with no documents leaves every project pointing at files that no longer exist.

Security15 min

Without it, rate limiting counts in memory — and on serverless each request may hit a fresh instance, so the sign-in throttle barely binds. The code warns about this in production, but the warning only helps if someone reads it.

  1. Create a free Redis database at upstash.com, in a region near your users.
  2. Copy the REST URL and token.
  3. Set UPSTASH_REDIS_REST_URL and UPSTASH_REDIS_REST_TOKEN in your host's environment variables, then redeploy.

Prove it

curl -H "Authorization: Bearer $CRON_SECRET" \
  https://yourdomain.com/api/cron/health-check

Must return "status":"ok". If rate limiting is still unconfigured it reports degraded and names it.

Do not skip10 min

This is the step that was missing before. Sentry was recording the Brevo failure correctly the entire time it was broken — nobody was told.

Sentry → Alerts → Create Alert → Issues. Trigger on a new issue is created, action: email you. Then add a second rule for an issue is seen more than 10 times in an hour, which catches a working feature that has started failing at volume.

Prove it

Sentry's alert editor has a Send Test Notification button. Use it, and confirm the mail arrives somewhere you will actually see it — not a folder you filter away.

10 min

Free tiers at UptimeRobot or Better Stack are more than enough. Monitor https://yourdomain.com/api/health every 5 minutes and alert on any non-200.

Do not monitor the homepage. It will keep returning 200 from cache while the database is unreachable and every signup is failing — which is precisely the outage you need to hear about.

Prove it

curl -i https://yourdomain.com/api/health

Expect 200 and {"status":"ok"}. A 503 means something is genuinely down — run task 4's command to find out what.

Blocks payment10 min

The invoice prints what you give it and invents nothing. Unset, it issues invoices with no address and no registration number, which a customer's accounts department will reject.

INVOICE_SELLER_NAME="TenderFlow AI"
INVOICE_SELLER_ADDRESS="your registered address"
INVOICE_SELLER_EMAIL="billing@yourdomain.com"
INVOICE_SELLER_RC="your CAC registration number"
INVOICE_SELLER_TIN=""   # leave blank until you have one

Leave INVOICE_TAX_RATE_PERCENT at 0 until you are registered for VAT with FIRS. Charging VAT without registration is an offence. When you do register, set it to 7.5 — no code change needed.

Prove it

Run one payment through Paystack in test mode. Check the invoice email arrives with a PDF attached, that the PDF carries your real address and RC number, and that the same invoice downloads from Usage → Invoices.

20 min

Three addresses are referenced in the product or its legal pages. An address that bounces is worse than none — the DPA naming a dead mailbox is a compliance failure by itself.

  • privacy@ — named in the Data Processing Agreement for data subject requests and breach notifications.
  • support@ — your support channel.
  • billing@ — whatever you used for INVOICE_SELLER_EMAIL.

Aliases forwarding to one inbox are fine. Then set ALERT_EMAIL to an address a person reads daily.

Prove it

Send a message to each from an outside account and confirm all three arrive.

30 min

A business buyer will ask what happens when something breaks. An honest, modest answer beats silence, and beats a promise you cannot keep.

Something like: "Email support@yourdomain.com. We reply within one business day, Monday to Friday, 9am–5pm WAT." Put it in the app footer and on the landing page.

Do not claim 24/7 or a one-hour response. A missed commitment in writing is worse than a modest one met every time — and enterprise buyers check.

Final gate45 min

On production, with a real email address you own and a real tender pack — ideally a long one, since that is what the chunking fix was for. Not the demo account, and not staging.

  1. Sign up. The confirmation email arrives in the inbox, not spam.
  2. Confirm the address and sign in.
  3. Create a project and upload a 60+ page tender pack.
  4. Check the checklist contains requirements from the last pages, not just the first few. This is the fix that mattered most; verify it on real output.
  5. Upload a scanned PDF. Either it is transcribed, or you are told clearly that it could not be read. An empty checklist with no explanation is a bug.
  6. Draft a section, then export to DOCX and PDF. Open both.
  7. Upgrade with a real card. Confirm the invoice email arrives with the PDF attached.
  8. Invite a teammate and confirm their invite arrives.
  9. Delete the test project, then the test account.

Prove it

Every step completes without you reaching for a database console or a log. If any step needs you to intervene, a customer hitting it will leave instead.

After you open the doors

Not launch blockers, but the first things to watch:

  • Re-verify the OCR quality. Transcription was built and its failure paths tested, but the free-tier quota was exhausted at the time, so the transcription itself has never run against a live model. Test it on a real scanned pack.
  • Watch AI cost. Chunking multiplies requests by the number of chunks. A 120-page pack is now five requests instead of one. Check the bill after the first week of real use.
  • Move DMARC to p=quarantine once reports are clean.
  • Sell to five customers by hand before opening it broadly. Watch each one use it. Compliance software gets exactly one reputation.
